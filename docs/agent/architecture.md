# Architecture

Read this when changing data flow, storage, auth, or folder boundaries. Only what the code cannot show on its own.

## Folder boundaries
- `app/`: Expo Router routes only. Thin files that render a screen from `components/wickglow`. `+html.tsx` is the web page shell; it must render `headNodes` and `bodyNodes` from `useServerDocumentContext()`, or the exported page has no scripts and stays on the dark loading screen.
- `src/core/`: pure logic (the session log and the progress rebuilt from it in `progress-log.ts`, how a device and an account combine in `sync.ts`, deadline math, phase cycle, XP, levels, streaks, quests, own-track playlist math, streaming-link parsing, which player owns the sound in `music-source.ts`, the ambient sound list in `ambient.ts`, what the timer shows around the time in `session-face.ts`, the timer limits and cycle length in `phase.ts`). No React, React Native, Expo or Firebase imports.
- `src/theme/`: shared color, font and radius tokens. No React. Screens read these instead of hardcoding colors.
- `src/data/`: the only place that talks to Firebase. `getFirebase()` returns `{ app, auth, db }` or null when the env config is missing, and the app then runs local-only. `firebase.ts` is Android and iOS (session kept in AsyncStorage through `getReactNativePersistence`), `firebase.web.ts` is web (session in IndexedDB). `auth.ts` (email sign-in, sign-out, verification, reset; errors become plain messages through `auth-errors.ts`), `google-sign-in.ts` (Android: the native picker from `@react-native-google-signin/google-signin`, loaded lazily so a build without the native module hides the button) and `google-sign-in.web.ts` (popup), `progress-remote.ts` (the `records` collection below: read everything, listen for what is new, push, reset; validates every record it reads).
- `assets/audio/`: licensed tracks only, listed in `MUSIC_LICENSES.md`.
- `assets/backgrounds/`: background videos, listed in `BACKGROUND_LICENSES.md`. Not all cleared yet; see that file's Status notes before wiring a new file into a scene picker.

### `components/wickglow/` is grouped by feature

- Root: `wickglow-screen.tsx` (the public entry `app/` imports), `logic.tsx` (the provider and context), `theme.ts` (scene and mood palettes, `PRESETS`, `formatTime`, and a re-export barrel for `src/theme/tokens` and six `src/core` modules).
- `screens/`: `mobile.tsx`, `tablet.tsx`, `desktop.tsx`. The device shells. Arrangement only, no business rules. Each is a thin composition of the feature panels. The start label, cycle line, pips and focus chip come from `sessionFace` (`src/core/session-face.ts`) and zen from `hooks/use-zen.ts`; a shell does not compute them itself.
- `features/`: one folder per product concept. `layout.ts`, `tone.ts`, `account/` (the account context, the Account row, the sign-in and keep-which-progress cards), `background/`, `clock/`, `timer/`, `tasks/`, `audio/`, `progression/`, `settings/`. A feature owns its own components; device differences are a `mobile` prop (or the shell), not a separate folder.
- `shared/`: `icons.tsx`, `panel-heading.tsx`, `panel-styles.ts`, `error-screen.tsx` (the route ErrorBoundary's UI), `web-scrollbar.ts` (the web scrollbar style the root layout installs), `web-input-zoom.ts` (16px text fields on touch screens, so a mobile browser does not zoom on focus; the root layout installs it). Cross-layout UI. `panel-styles.ts` is the one `StyleSheet` the feature panels share.
- `hooks/`: `use-ambient`, `use-background-audio`, `use-music`, `use-session-clock`, `use-zen`. Kept together rather than scattered per feature.
- `domain/`: `saved-state.ts`, `saved-store.ts`, `save-queue.ts`, `session-run.ts`, `notifications.ts`, `storage.ts`, `own-music.ts`, `preload-track.ts` (plus `preload-track.web.ts`, its web sibling, which must keep the same basename), `silence-ambient.ts`, `stream-check.ts`, `account-sync.ts` (links the store to the signed-in account; see Auth and access). Non-UI: persistence, scheduling, file picking and copying, and platform wrappers. Code outside `components/` imports `src/core` directly. Tests sit beside their file (`*.test.ts`).

### session.ts is the reward path

`completeSession` in `src/core/session.ts` is the one path for a finished focus. It pays 2 XP per minute, adds the minutes, and, when the session is at least `SESSION_REWARD_MINUTES` (10) from `src/core/xp.ts`, counts one session and updates the streak. Quest payouts stay in `quests.ts`. No component computes XP. Goals were removed on 2026-11-04.

### Layout switching is dimension-driven
`features/layout.ts` holds the only breakpoint logic (`PHONE_MAX_WIDTH` 600, `TABLET_MAX_WIDTH` 840, `layoutForWidth`, `layoutForWindow`). It is **not** in `theme.ts`.

The check is dimensions, never device model: an iPad in portrait (shorter side 768-834) gets the tablet layout, and an iPad Pro in landscape (shorter side 1024) gets the desktop scene because 1024 is past 840. So "tablet" is a width band, not "iPad". Android is the only verified target; iOS is untested.

### Two contexts, and actions that never change

`logic.tsx` provides two contexts. `useWickglow()` is the state and the actions; its value is memoised and changes only when something on screen changes. `useWickglowClock()` is the countdown (`remaining`, `progress`), which changes every second while a session runs. Only `TimeText` and `SessionCandle` read the clock. Do not read it in a screen shell or a panel, or that whole component re-renders every second.

Every action from `useWickglow()` keeps one identity for the life of the provider (`useStableActions`). A new action must be added to `WickglowActions` and to `ACTION_NAMES`; the compiler refuses the build if the second is forgotten. Destructure actions at the top of a component rather than calling `lamp.action()`.

## Storage model
- Device (AsyncStorage, one JSON value under `wickglow:state`): tasks, settings, XP, streak, daily quest progress, the current session. It is the source the app reads from, signed in or not; Firestore is a copy it syncs with. There is no Zustand; the provider in `logic.tsx` holds the state. On web, open tabs share that one key: a `storage` event from another tab replaces the state here without a write (`SavedStore.adopt`).
- Writing: `domain/saved-store.ts` holds the newest state and is the only thing that changes it. The provider reads it with `useSyncExternalStore`. `store.commit` writes at once (timer changes). `store.update` is written by `domain/save-queue.ts` 300 ms after the last change, and at once when the app leaves the foreground.
- Timer changes: `domain/session-run.ts` owns start, pause, reset, skip, mode and length changes, and the session end. It is the only caller of `scheduleSessionEnd` and `cancelSessionEnd`, which is how the one-alarm rule in `AGENTS.md` is kept. It takes the alarm, the music, the time and the screen effects as arguments, so its tests run it without a device. A new timer action goes there, not in `logic.tsx`.
- Music source: `src/core/music-source.ts` decides whether the local player, an embed or another app owns the sound. `logic.tsx` sends it events (`sendSource`) and carries out the pause or play it returns.
- Reading: `parseSavedState` checks every field and builds the state from the known fields only, so an unknown key is dropped.
- The session log (2026-11-13): `log` in the save holds every finished focus session as a record (`{ id: "{end}-{minutes}", end, minutes, task }`, appended by `completeSession`; `task` is the focused task, so each device counts a task's sessions itself with `withSessionCounts`) and `legacy`, one record per day of the daily totals a save had before the log existed (made once by `parseSavedState`). While signed out the app keeps updating `xp`, `streak` and `days` as before. While linked to an account, every sync rebuilds them from the log and the tasks (`rebuildProgress`), so two devices agree.
- Firestore (accounts, 2026-11-13; one collection since the read-cost fix): everything is in `users/{uid}/records`, so "anything new?" is one query. `s_{end}-{minutes}` a session `{ kind, end, minutes, task, day?, at }` (create-only; `day` is the writer's local day, which every device files it on, since 2026-11-14); `d_{calendarKey}` a pre-log day total `{ kind, minutes, sessions, tasks, at }` (create-only); `t_{taskId}` a task `{ kind, text, done, doneOn, parentId, date, updatedAt, deleted: false, at }` or its tombstone `{ kind, deleted: true, updatedAt, at }`; `reset` `{ kind, epoch, at }`. `at` is the server write time, which the rules require. A task's open subtask list and its session count are not stored there. No XP, level or streak is stored. Rules in `firestore.rules`, tested with the emulator in `firestore-tests/`.
- Sync (`domain/account-sync.ts`, rules in `src/core/sync.ts`): `sync` in the save is what the device last saw in the linked account, including `since` (the newest server time it has read) and `epoch` (the account's reset count). A linked device listens only for records with `at` at or after `since`, so an app open with nothing new costs about one read however long the history is. A record the account never confirmed is pushed. Only server-confirmed copies count as seen (`listenProgress` skips cached copies and ones with our writes pending), so a write that never landed is sent again rather than lost. Tasks: the latest edit wins and a delete wins. An edit is stamped when it is made, not when it is sent (`sync.edits`, noted by the store listener in `account-sync.ts`, kept until the account confirms it), and the rules refuse a task edit older than the stored one. Deleting a finished task keeps its credit: the log keeps it in `log.finished`, its tombstone carries `doneOn` and is never cleared, and `rebuildProgress` counts it on the day it was finished (reopening a task still takes the credit back); a tombstone is deleted after 30 days (`TOMBSTONE_KEEP_MS`), by any device that saw it. A full read (everything) happens only on first sign-in, on a new device, when a device was away more than 30 days (it could have missed a cleared tombstone; measured from `sync.checked`, the device's own time of its last confirmed read, since `since` stays old while nobody writes), and when the reset count goes up. Every record carries `epoch`, the reset it was written under, and the rules refuse one that does not match the `reset` marker (0 before the first). The marker cannot be deleted, so the count only goes up. A task with an edit sent and not yet confirmed is kept as edited (its seen `sig` is blanked) until a confirmed read settles it, so an undo back to the confirmed text before then is not lost to the confirmation. Keeping this device's progress over the account's is one write, raising `reset`: from then on every device ignores records from an older reset, and `progress-remote.ts` deletes them (that reset, or any later full read, finishes a cleanup cut short). Other devices then read everything once and drop what is gone. Uploads go one write per record at a time; one held back because an earlier write for it was still out is sent once that settles. The status reads "Saving to your account" (`saving`) while any sent write is unacknowledged, and "saved" only once all are. A session or day record the account already holds is counted as saved, not as a refused write. Sends: 1.5 s after a finished session, 10 s after the last task edit (a burst is one write per task), and at once when the app leaves the foreground. Signing out clears the progress (XP, streak, tasks, history and the link to the account) from the device and keeps its settings, so the next account to sign in there cannot take it (owner, 2026-11-14). It first sends anything waiting and waits up to 4 s for the account to confirm it; if some is still unsaved (offline, a failed save, "Decide later"), a card warns, with Stay signed in and Sign out anyway. `AccountSync.stop` (the session ended without a sign-out) still keeps everything. Read-cost estimates are in `docs/feature/firebase.md`.
- Daily minutes: keep one total per day on the device without pruning, so the calendar has history. The month grid reads that history through `monthGrid` and stores nothing of its own; only the displayed month and the tapped day live in the panel's state.
- Audio files: bundled in `assets/audio` for v1. The user's own files are copied into the app's private document folder (`Paths.document/own-tracks`) and only their id, title and `file://` URI are stored in AsyncStorage. A streaming link stores the public page URL and the service name in the same save. The audio stays in that service's player. Do not store audio in database rows, and do not copy a stream into a file.
- Background videos (2026-11-13, to keep the Android download small): only Classic is bundled. Every other video and pixel-art scene is a static file in `public/scenes/` (owner choice, 2026-11-13). The web export copies `public/` into `dist`, so Vercel serves them at `https://wickglow.vercel.app/scenes/...`, which is `SCENE_HOST` in `src/core/remote-scenes.ts` (a public address, not an env var). Web loads them from the same site (`SCENE_WEB_PATH`, `/scenes`), so the dev server and preview deploys serve their own copy. A new scene only reaches Android once the web deploy that holds it is live. If traffic outgrows Vercel's free plan, move the folder to another file host and change `SCENE_HOST`. Catalog entries in `video-art.ts` and `pixel-art.ts` carry `{ path, bytes }`; the path has a version folder (`v1/...`), so a re-encoded file must get a new version and its new byte size. Android downloads a scene on tap into `Paths.document/scenes` (`domain/scene-files.ts`, written as `.part` and renamed only when the size matches) and plays it offline; web streams it from the host (`scene-files.web.ts`). `features/background/scene-downloads.ts` holds the shared status. A picked scene that is not on the device plays Classic instead. While `SCENE_HOST` is empty the remote tiles are hidden. Nothing `require`s the files in `public/scenes/`, so they are never in the app bundle. A missing file makes Vercel's catch-all rewrite answer with the web page, which the size check rejects, so the tile shows "Tap to retry".

## Auth and access
Built 2026-11-13. Firebase project `wickglow` (id `wickglow-a70f4`, in `.firebaserc`), Spark (free) plan, Firestore created in production mode (deny all) until `firestore.rules` is deployed (`npm run deploy:rules`).

- Authentication: Firebase Auth, optional. Local-only use keeps working. Methods: Email/Password and Google. Authorized domains include `wickglow.vercel.app`.
- Ownership: every document sits under the signed-in user's `uid` and the rules match `request.auth.uid`.
- Access control: Firestore security rules, a user reads and writes only their own documents. With no Cloud Functions on Spark, the rules are the only server check on XP, streak and quest rewards: they limit what a single write can add, not the total, and cannot recompute anything. A session write is at most 180 minutes (360 XP plus the daily quests), a day record at most 1440 minutes, and a task write moves one day's task count by one. Nothing stops a modified client from writing many sessions, so account XP is not trustworthy for comparing users; that is fine while nothing compares XP (no leaderboards, circles or rooms).

## Invariants
Check these before finishing a task. Timer, notification, audio and navigation rules are in `AGENTS.md`.
1. `src/core` imports nothing from React, React Native, Expo or Firebase.
2. Layout components contain no business rules.
3. Firestore rules deny by default; every allowed path checks `request.auth.uid`.
4. Only `src/data` imports Firebase.

## Decisions and why
- Sync progress as session records, not totals. Why: owner choice, 2026-11-13; with no server to recompute rewards, records are what the rules can bound and two devices can combine without double counting. Trade-off: a quest claimed and then undone (a task unticked) is unclaimed after a sync, where the device on its own keeps it. Date: 2026-11-13
- Firebase over Supabase (replaces the 2026-11-01 Supabase choice). Why: owner choice, on the free Spark plan. Trade-off: no Cloud Functions, so rewards are bounded by security rules instead of recomputed on a server. Date: 2026-11-13
- Firebase JS SDK, not `@react-native-firebase`. Why: one SDK for web and Android, no `google-services.json` or native module. Date: 2026-11-13
- Keep hosting on Vercel, not Firebase Hosting. Why: Android downloads scenes from `wickglow.vercel.app`, and Spark's hosting transfer (about 360 MB a day) is too small for the videos. Date: 2026-11-13
- Expo SDK 58 with Expo Router. Why: stable since mid October 2026, and the app uses few third-party native libraries. Date: 2026-11-01
- Timestamp timer with a scheduled notification, no custom foreground service. Why: a foreground service is the wrong Android tool for a countdown. Date: 2026-11-01
- One local notification on the `session-end` channel, scheduled at `endAt` with `delivery: 'alarmClock'` and `USE_EXACT_ALARM`. Why: Wickglow is a timer, and Google Play allows that permission for timer apps. `bestEffort` can be deferred by minutes on some Android builds. Date: 2026-11-02
