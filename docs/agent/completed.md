- Review fix, 2026-11-06. - Music starting behind the timer, 2026-11-04. Pressing Start began the track late on every platform, worst on web. Two causes. On native, `begin` awaited `prepareNotificationPermission` before touching the player, and that helper deletes and recreates the notification channel and queries permissions on every start — a chain of native round trips on the path to `play()`. `begin` now starts the track first and asks for the permission after, committing the clock and the `notificationsAsked` flag in one write once it resolves. On web the player only opens a connection to a source when `play()` is called, so the first press of Start fetched the whole track: the bundled files are 3.5 to 6.9 MB, which measured 12.5 seconds to fetch on a 6 Mbps link, and that fetch is what put the music behind the timer. `domain/preload-track.ts` and its `.web.ts` twin warm the cache while the player is idle; on web the platform file awaits the module's own `preloadAsync`, which the public `preload` discards there, and the hook swaps the element onto the cached copy before playback. `useMusic` takes the web branch only, since native players stream on their own. The swap is skipped once the player is playing or past the start, and volume and loop — which a replaced element resets — are reapplied with it. Measured in Chrome over CDP: Start to audible 69 ms at 6 Mbps, against the same build fetching cold. Web only; the native ordering change is not yet checked on a device.
